# Desarrollo de Ejercicios - Prueba eDecision

## Introducción

Este documento lleva a cabo el desarrollo de los ejercicios de la prueba técnica de la empresa **eDecision**. Los ejercicios se detallan como parte del desarrollo de este documento, por lo cual podrán ser consultados con facilidad. 

## Objetivo
Establecer el entregable de la prueba técnica para la oferta laboral de **Desarrollador Fullstack Semi Senior** en la empresa **eDecision**, a la cual postulé como candidato.

### Ejercicio 1.1 (Backend / API)

```javascript
app.get("/api/orders", async (req, res) => {
  const userId = req.query.userId;
  const orders = await db.query(
    `SELECT * FROM orders WHERE user_id = ${userId}`,
  );

  for (const order of orders.rows) {
    const items = await db.query(
      `SELECT * FROM order_items WHERE order_id = ${order.id}`,
    );
    order.items = items.rows;
  }

  res.status(200).json(orders.rows);
});
```

Se solicita:

1. Encontrar, al menos, 8 problemas o riesgos.
2. Explicar qué riesgos son de seguridad, rendimiento, mantenibilidad y diseño de API.
3. Proponer una versión mejorada del endpoint o pseudocódigo equivalente.
4. Explicar qué indices o ajustes de base de datos consideraría.

---

## 1. Problemas o riesgos identificados

1. **Acoplamiento de lógica de negocio:** La implementación realiza toda su funcionalidad como parte de la ejecución de un sólo método. Usualmente se manejan instancias que desacoplan la funcionalidad, facilitando el testing. En Spring Boot usamos los beans `@Service`, por ejemplo.

2. **Riesgo de inyección SQL:** el endpoint permite inyectar datos a través del parámetro de url `userId`.

3. **Problema N+1:** al consultar de forma iterada los registros de `order_items` para cada orden inicial obtenida.

4. **Gestión de Excepciones:** Falta manejo de excepciones para llamados a persistencia. Si el manejador (o handler) `async` rechaza la promesa, el cliente podría quedarse esperando sin respuesta, la petición podría quedar colgada o terminarse el proceso en el servidor de forma impredecible. Además, en caso de presentarse algún error, con la implementación actual se filtrarían detalles internos al cliente.

5. **Sin autenticación ni autorización:** No existe mecanismo de autenticación para consumir el endpoint actual, por lo que cualquier cliente podría consumirlo. Además, no existe mecanismo de autorización que permita identificar al servidor si el cliente que envía la petición tiene permitido consultar el recurso que solicita.

6. **Sin validaciones:** El endpoint no hace validaciones esenciales, como si `userId` es número entero positivo o si tiene el formato esperado, no devuelve un código de estatus 400 _(Bad Request)_ si la información de petición no es correcta. Si no se enviara un `userId` en la petición, por ejemplo, con la implementación actual se estaría intentando traer los registros para un id de usuario `undefined`, lo cual generaría fallos en las consultas.

7. **Consulta de todos los campos en las tablas:** Las consultas SQL intentan obtener **todos los campos** de cada item, esto implica que información sensible podría viajar en dicha consulta, además de información que seguramente no es relevante para las reglas de negocio que se están ejecutando.

8. **Consulta de registros sin límite:** Ninguna de las dos consultas SQL se encuentra **limitada**. Esto implica que todos los registros serán consultados. Por ejemplo, si un usuario tiene **200.000 órdenes** asociadas, las consultas intentarán obtener toda esta información y, por cada órden, se intentarán obtener todos los items asociados.

## 2. Clasificación de Riesgos

Los riesgos identificados se clasifican de la siguiente manera:

seguridad, rendimiento, mantenibilidad y diseño de API.

| N°  | Problema o Riesgo                          | Tipo de Riesgo                                         | Descripción                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Acoplamiento de lógica de negocio          | Mantenibilidad                                         | Al tener toda la lógica implementada en una única función, los componentes que conforman la funcionalidad quedan con un acoplamiento fuerte, lo que hace más dificil probar el funcionamiento o comportamiento esperado del endpoint, además de hacer más dificil la depuración de bugs. Se mitiga especificando componentes o capas con responsabilidades específicas                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 2   | Riesgo de inyección SQL                    | Seguridad                                              | El endpoint permite que se inyecte código SQL en el parámetro que se recibe, lo cual puede generar fuga de datos internos. Se puede mitigar si se usan consultas parametrizadas y validación sobre el parámetro                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 3   | Problema N+                                | Rendimiento                                            | Se consulta un listado de órdenes, y por cada órden se consultan los items correspondientes, como resultado se producen múltiples viajes hacia la base de datos, impactando directamente el rendimiento del servidor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 4   | Gestión de Excepciones                     | Seguridad y Mantenibilidad                             | Sin una correcta gestión de excepciones, cualquier proceso que se invoque desde la implementación podría fallar, por ejemplo, llamados asíncronos a persistencia. Un fallo que no se gestione correctamente dentro de cualquiera de los procesos ejecutados podría filtrar información interna del negocio al cliente, además de contribuir a una mala experiencia en el consumo del endpoint. Es también un riesgo de mantenibilidad porque una API REST sin gestión de excepciones no brinda robustez ni confiabilidad, características clave de un software bien mantenido. Se mitiga identificando las invocaciones clave a procesos con riesgo potencial de producir excepciones o fallos, y gestionando de forma apropiada las excepciones.                                                                                                                                                                                                                                                                                                                                 |
| 5   | Sin autenticación ni autorización          | Seguridad                                              | Una API REST que no ofrece autenticación y autorización es altamente insegura. Sin un control de acceso y autorización, la API expone datos sensibles a sus usuarios, como consecuencia se pueden producir robos graves de datos sensibles y pérdida de la credibilidad del negocio. Yo mitigaría este riesgo obteniendo el `userId` no como parte del parámetro en la URL de petición, sino de una instancia de sesión, de esta manera no exponemos el `userId` directamente en la URL de petición. Esta instancia se inicializa como parte de la autenticación del usuario, por lo que también se requiere asegurar el endpoint.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 6   | Sin Validaciones                           | Seguridad y Mantenibilidad                             | El endpoint no hace validaciones de tipo y valor sobre `userId`, haciendo posible que el cliente no envíe nada como parámetro y afectando directamente el comportamiento del endpoint. Esto es además inseguro, porque un fallo durante el proceso de este endpoint podría filtrar información interna al cliente.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 7   | Consulta de todos los campos en las tablas | Seguridad, Mantenibilidad, Rendimiento y Diseño de API | Este riesgo tiene impacto en los 4 tipos de riesgo. Es inseguro consultar todos los campos de las tablas. El cliente recibe información que **no necesita**. Sin control de acceso toda esta información se expondría directamente al cliente. La mantenibilidad del endpoint se ve impactada ya que se requiere escribir código que encapsule cada campo devuelto por las consultas, así como la lógica encargada de que el mapping entre campos sea correcto. Consultar todos los campos de cada tabla impacta en el rendimiento al tener que procesar todos los campos como objetos en memoria dentro de la aplicación, haciendo que sea más lento el consumo del endpoint. El Diseño de API también se impacta con este riesgo ya que se requiere ajustar el contrato de este endpoint para que refleje todos los datos consultados y expuestos. Mitigaría este riesgo consultando únicamente los campos necesarios de la tabla, refactorizando la implementación para que se expongan únicamente los datos necesarios, y ajustando el contrato del endpoint en consecuencia. |
| 8   | Consulta de Registros Sin Límite           | Rendimiento                                            | La implementación actual no limita los registros que consulta. Si un `userId` tuviera asociadas 10.000 órdenes, la consulta de órdenes intentará devolver todos los registros, impactando directamente en el rendimiento del servidor, además de contribuir al problema de N+1 ya mencionado.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
